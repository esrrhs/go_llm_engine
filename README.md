# go_llm_engine

面向弱模型（小参数、低算力、廉价模型）的自动化编程与工程构建 Agent。

---

## 1. 核心理念与设计方案

### 1.1 背景与定位
现有的编程 Agent（如 Claude Code 等）极度依赖前沿高智商、超长上下文的旗舰模型（如 Claude 3.5 Sonnet、GPT-4o）。这些模型具备强大的全局抽象与长链推理能力，但在面对小模型或低成本开源模型（如 7B/8B/14B、低配云端 API）时，传统方案容易出现：
* **上下文爆炸（Context Overflow）**：历史越长，模型注意力漂移、遗忘前置约束或产生幻觉。
* **推理过载（Reasoning Overload）**：一次性规划过多细节导致逻辑崩溃或代码残缺。

**`go_llm_engine` 的定位是：“愚公移山，分而治之”。**
不追求单次规划与执行的极速，只追求通过工程架构的严密约束，确保最终**百分之百能稳健交付**复杂目标。

---

### 1.2 核心设计机制

```
                     ┌───────────────────────┐
                     │ 根目标 Root Task      │
                     │ (例: "实现一个操作OS") │
                     └──────────┬────────────┘
                                │ 递归拆解
               ┌────────────────┴────────────────┐
               ▼                                 ▼
      ┌─────────────────┐               ┌─────────────────┐
      │ 子任务: 内存管理 │               │ 子任务: 进程调度 │
      │ [接口契约+验收标]│               │ [接口契约+验收标]│
      └────────┬────────┘               └────────┬────────┘
               │ 递归拆解                        │ 递归拆解
         ┌─────┴─────┐                     ┌─────┴─────┐
         ▼           ▼                     ▼           ▼
    ┌─────────┐ ┌─────────┐           ┌─────────┐ ┌─────────┐
    │叶子任务A│ │叶子任务B│           │叶子任务C│ │叶子任务D│
    │(微小任务)│ │(微小任务)│           │(微小任务)│ │(微小任务)│
    └────┬────┘ └─────────┘           └─────────┘ └─────────┘
         │
         ▼ 最小化上下文投影 (仅注入当前接口定义 + 当前文件片段)
    ┌───────────────────────────┐
    │ 独立上下文执行器 (Worker) │ ────> 强校验 (编译/单测通过) ────> 标记完成
    └───────────────────────────┘
```

1. **树状递归微任务分解（Tree-Structured Task Decomposition）**
   - 复合任务逐层分解，形成严格的树状/DAG拓扑。
   - 非叶子节点充当“架构师”与“拆解者”，负责：明确子模块边界、**制定接口契约（Interface Spec）**与**量化验收标准（Definition of Done）**。
   - 只有最小粒度的单一任务才能作为叶子节点落地执行（例如：只实现某个单一函数、补齐一个结构体定义、针对某接口编写单一测试用例）。

2. **接口规范与验收标准（Contract & DoD Prioritization）**
   - 任何任务在被下发执行前，必须具有清晰的：
     - **输入/输出约束（Interface Contract）**：依赖的数据结构、签名、外部依赖。
     - **验收判定（Verification Command / Test）**：自动化执行命令（单测、编译、语法检查、断言输出等）。
   - 任务不通过验收标准，即视为失败，触发局部的局部自愈、反思或进一步拆分。

3. **叶子节点独立上下文隔离（Isolated Context Sandbox）**
   - 叶子节点在执行时拥有全新的、干净的极简上下文，**彻底阻断长会话历史污染**。
   - 仅注入：
     1. 当前节点明确定义的任务目标
     2. 父级与其直接依赖的接口规范（Spec）
     3. 关联的极少量代码切片（相关文件/函数）
     4. 验收标准与验证命令
   - 单次执行无论消耗多少 Token，执行完并验收后即归档销毁上下文，杜绝上下文爆炸。

## 2. 系统模块设计

1. **Task Tree Engine（任务树状态引擎）**
   - 任务树数据结构（节点元数据、层级依赖、任务状态机）。
   - 状态机流转：`PENDING` -> `PLANNING/DECOMPOSING` -> `RUNNING` -> `VERIFYING` -> `COMPLETED` / `FAILED`。
   - 本地持久化与断点续跑（支持执行中断后重新加载树状态继续执行）。

2. **Decomposer（任务拆解与契约定义器）**
   - 面向弱模型的标准化 Prompt 模板，强制输出结构化 JSON/YAML。
   - 负责评估当前节点是否足够简单：
     - 若复杂度过高，继续拆分并定义子任务的验收标准与接口签名。
     - 若已达到原子执行粒度，标记为叶子节点（Leaf Node）。

3. **Leaf Worker & Tool Sandbox（叶子执行器与工具沙箱）**
   - 隔离的执行上下文环境。
   - 极简、鲁棒的原子工具集：`read_file`、`write_file`、`replace_lines`、`run_bash`、`list_dir`。
   - 保证只给小模型最少且必要的工具描述，减少小模型工具调用的格式错误。

4. **Verifier & Auto-Healing（验收与自愈机制）**
   - 叶子任务执行完毕后，自动化触发该节点的验收测试命令。
   - 验证成功：合并状态，向上通知父节点。
   - 验证失败：在当前隔离上下文带上错误输出进行重试（限制最大重试次数）；超出重试阈值则触发任务树重构（重新拆解）。

5. **Terminal UI & Progress Monitor（终端交互与可视化）**
   - 类似 Claude Code 的 CLI 终端交互体验。
   - 树状进度实时渲染、当前活跃叶子节点状态、全局完成率统计。

  - [x] 1.2 实现任务树数据模型（TaskNode、TaskTree、状态定义、接口契约结构体）。
  - [x] 1.3 实现任务树的本地存储、序列化与加载（断点恢复能力）。
  - [x] 1.4 实现树遍历调度器（自顶向下分解、自底向上验收、依赖拓扑排序）。

- [ ] **阶段 3：任务拆解器与契约定义（Decomposer & Contract Generator）**
  - [ ] 3.1 设计分层拆解 Prompt：输入目标 -> 输出原子子任务列表 + 接口规范 + 验收单测命令。
